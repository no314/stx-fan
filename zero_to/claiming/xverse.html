Why Xverse is not supported yet

This app works with Leather only, because Xverse cannot sign its calls safely today. The reasons below are read from Xverse's own sources, with what would change them.

What this app needs from a wallet

Two capabilities keep your funds safe when you sign, and the app requires both.

network on connectThe app passes the target network to connect(), so the wallet connects to the network you intend. Without it, a wallet can default to mainnet while its active account differs from the one you are connecting. With real STX that mismatch is dangerous.
originator mode on every callEach call this app sends runs in originator post-condition mode on stx_callContract. The calls are claim-rewards, claim-staker-rewards, settle-staker-rewards, payout, withdraw-fees and the batch helpers' claim-many, settle-many and payout-many. In that mode nothing can leave the caller's wallet, while the manager and pox-5 may still move the sBTC reward to the staker. Plain deny with no conditions would abort every claim at the manager's own transfer, and allow would leave the caller unprotected. The app declares the mode and the protocol enforces it, but only when the wallet passes it through. A wallet that rejects or rewrites it cannot sign these calls safely.

Where Xverse falls short today

The findings come from Xverse's own method documentation and from its sats-connect-core library, not from third-party compatibility tables. The library files are SIP030_COMPARISON.md and the stx_callContract request schema, repository state of 2026-09-15.

No originator mode. Xverse accepts post-conditions on stx_callContract and stx_deployContract as hex-encoded strings, and a postConditionMode. Its schema defines that mode as 'allow' | 'deny' and nothing else. This app sends originator on every call. Xverse's schema refuses that request before signing. The alternatives, allow (unprotected) and deny (every claim reverts), are ones this app never sends, so it blocks Xverse instead of dropping your protection. Whether the closed-source extension enforces exactly what its published schema accepts cannot be checked. The schema is the contract an app can rely on.

No network parameter. Xverse's own comparison lists "No network parameter support" as an open gap. Neither connect nor the transaction methods take the target network, so the first requirement above cannot be met either.

The same comparison states that Xverse implements stx_getAddresses and lacks stx_transferSip10Ft, stx_transferSip9Nft, stx_getNetworks and stx_updateProfile. This app uses none of those four.

What would change it

SIP-030 lists postConditions, a postConditionMode of 'allow' | 'deny' and a network parameter among its general transaction parameters. The originator mode this app relies on is the protocol's newer, caller-scoped mode. It makes a claim safe for the person signing it without listing every transfer the manager and pox-5 make on the way. Two changes in Xverse would make it usable by apps like this one.

1. Accept originator as a postConditionMode on stx_callContract and stx_deployContract, next to allow and deny, and pass it through unchanged to the signed transaction.
2. Accept the network parameter on connect and on the transaction methods, as SIP-030 lists it, so an app can name the network it intends.

Once both land, enabling Xverse here is a small change on this side.

Sources: Xverse docs, stx_callContract · sats-connect-core SIP030_COMPARISON.md · sats-connect-core stx_callContract request schema

Why this matters beyond this app

Leather and Xverse are the two most-used Stacks wallets. When the two accept different post-condition modes, each builder faces the same choice. Drop safety to reach both wallets, or support one and lose the other's users. One wallet standard that keeps up with the protocol's post-condition modes lets one app run safely in every wallet.
