Why Xverse isn't supported (yet)

This app currently works with Leather only. Xverse can't be used yet: not a preference, a safety limit. Here is exactly why, read from Xverse's own sources, and what would change it.

What this app needs from a wallet

Two capabilities are non-negotiable, because they are what keep your funds safe when you sign:

network on connectThe app passes the target network to connect() so the wallet connects to the network you intend. Without it, a wallet can silently default to mainnet when its active account differs from the one you are connecting: a dangerous mismatch when real STX is involved.
originator mode on every callEvery call this app sends (claim-rewards, claim-staker-rewards, settle-staker-rewards, payout, withdraw-fees, the batch helpers' claim-many, settle-many, payout-many) runs in originator post-condition mode on stx_callContract: nothing can leave the caller's wallet, while the manager and pox-5 contracts are still allowed to move the sBTC reward to the staker. Plain deny with no conditions would abort every claim at the manager's own transfer; allow would leave the caller unprotected. The mode is declared by the app and enforced by the protocol, but only if the wallet actually passes it through; a wallet that rejects or rewrites it cannot sign these calls safely.

Where Xverse falls short today

Read from Xverse's own method documentation and the request schema in its sats-connect-core library (its SIP030_COMPARISON.md and stx_callContract request schema, repository state of 2026-09-15), not from third-party compatibility tables:

No originator mode. Xverse does accept post-conditions on stx_callContract and stx_deployContract (as hex-encoded strings) and a postConditionMode, but its schema defines that mode as 'allow' | 'deny' and nothing else. This app sends originator on every call. A request that Xverse's schema does not accept is refused before signing, and the only alternatives, allow (unprotected) or deny (every claim reverts), are not ones this app will send. So it blocks Xverse rather than quietly dropping your protection. Whether the extension itself enforces exactly what its published schema accepts cannot be checked, since the extension is closed source; the schema is the contract an app can rely on.

No network parameter. Xverse's own comparison lists "No network parameter support" as an open gap: neither connect nor the transaction methods take the target network, so the first safety requirement above cannot be met either.

For completeness, the same comparison states that Xverse implements stx_getAddresses, and that it lacks stx_transferSip10Ft, stx_transferSip9Nft, stx_getNetworks and stx_updateProfile. None of those four is used by this app.

What would change it

SIP-030 lists postConditions, a postConditionMode of 'allow' | 'deny' and a network parameter among its general transaction parameters. The originator mode this app relies on is the protocol's newer, caller-scoped mode: it is what makes a claim safe for the person signing it without listing every transfer the manager and pox-5 make on the way. To be usable by apps like this one, Xverse would need to:

1. Accept originator as a postConditionMode on stx_callContract and stx_deployContract, next to allow and deny, and pass it through unchanged to the signed transaction.
2. Accept the network parameter on connect and on the transaction methods, as SIP-030 lists it, so an app can name the network it intends.

Once those land, enabling Xverse here is a small change on this side.

Sources: Xverse docs, stx_callContract · sats-connect-core SIP030_COMPARISON.md · sats-connect-core stx_callContract request schema

Why this matters beyond this app

Leather and Xverse are the two most-used Stacks wallets. When the two accept different post-condition modes, every builder faces the same bad choice: drop safety to reach both wallets, or support only one and lose half the users. A single, fully-implemented wallet standard that keeps up with the protocol's post-condition modes is what lets one app run safely in every wallet.
