## 2. Contradictions and corrections (most valuable output)

Numbered; each says what the prompt or earlier note claimed, what the source says, and what changed.

1. **"HODLLM" does not exist.** No contract by that name on mainnet. Bitflow's product is **HODLMM**, deployed as the DLMM contracts. The STX/sBTC pool is `SM1FKXGNZJWSTWDWXQZJNF7B5TV5ZB235JTCXYXKD.dlmm-pool-stx-sbtc-v-1-bps-15` (pool id u6, bin step 15 bps, `x-token` `SM1793C4R5PZ4NS4VQ4WMP7SKKYVH8JZEWSZ9HCCR.token-stx-v-1-2`, `y-token` `SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token`, fees x/y protocol 25 + provider 25 bps, variable 0) with core `SP1PFR4V08H1RAZXREBGFFQ59WB739XM8VVGTFSEA.dlmm-core-v-1-1` (read from `pool-addresses`, `pool-info`, `pool-fees` data vars). Route A uses these.

2. **The DLMM core has no quote function and swaps one bin per call.** `swap-y-for-x (pool-trait x-token-trait y-token-trait bin-id int y-amount uint) -> (ok {in, out})` asserts `(is-eq bin-id active-bin-id)` (ERR_NOT_ACTIVE_BIN u1047) and caps the input at the active bin's capacity: `(updated-y-amount (if (>= y-amount updated-max-y-amount) updated-max-y-amount y-amount))`. The prompt assumed a swap and a quote entrypoint. The contract walks up to `DLMM_MAX_BINS` (10) bins per `convert` and quotes by mirroring the core arithmetic (`dlmm-quote-step`), reading `get-pool-for-swap`, `get-bin-balances` and `get-bin-price`. Whatever a tranche cannot fill stays in the epoch. Admin surface of the core: `set-pool-status` (disable), `set-x-fees`/`set-y-fees`/`set-variable-fees`, core migration (`migrate-pool`, cooldown at least one week, `MIN_CORE_MIGRATION_COOLDOWN u604800`), `swap-fee-exemptions` per caller.

3. **Velar's STX/sBTC pool is not in `univ2-core`.** `univ2-core` holds 87 legacy pools (`pool-id` data var 0x57). The STX/sBTC pool is an "amm2" standalone pool: `SP20X3DC5R091J8B6YPQT638J8NR1W83KN6TN5BJY.univ2-pool-v1_0_0-0070` with `SP20X3DC5R091J8B6YPQT638J8NR1W83KN6TN5BJY.univ2-fees-v1_0_0-0070` (swap fee 9970/10000, protocol 2500/10000, owner may lower `swap-fee.num` to 9950, i.e. 0.50 percent max) and LP token `SP20X3DC5R091J8B6YPQT638J8NR1W83KN6TN5BJY.univ2-lp-token-v1_0_0-0070`. Its `swap (token-in <ft> token-out <ft> fees <fees-trait> amt-in amt-out-desired)` computes `amt-out` through `SP1Y5YSTAHZ88XYK1VPDH24GY0HPX5J4JECTMY4A1.univ2-math find-dx` and asserts `(>= amt-out amt-out-desired)`. The documented `univ2-router swap-exact-tokens-for-tokens` is for legacy core pools and does not reach this pool. No pause function exists on the pool; fees are the only owner lever. Quote: pool `get-pool` (reserves) + fees `calc-fees` + math `find-dx`, all read-only. Route B uses these. The Velar SDK API (`sdk.velar.network/pools/paths/...`) identified the pool (`poolType: "amm2"`); `api.velar.co` reported reserves and TVL.

4. **A third STX/sBTC pool exists and was not used**: Bitflow XYK `SM1793C4R5PZ4NS4VQ4WMP7SKKYVH8JZEWSZ9HCCR.xyk-pool-sbtc-stx-v-1-1`, 127,242 STX + 0.4747 sBTC, about 75k USD per Bitflow's ticker. Shallower than Velar; listed for completeness.

5. **Block limits.** The earlier note's 30,000 reads / 200 MB per tenure is correct for epoch 4.0: stacks-core `stackslib/src/core/mod.rs` at tags 4.0.1 and 4.0.2 both define `BLOCK_LIMIT_MAINNET_40 { write_length: 15_000_000, write_count: 15_000, read_length: 200_000_000, read_count: 30_000, runtime: 5_000_000_000 }` with the comment "Block limit in Stacks 4.0. Same as 2.1, except the read budget is doubled", wired to `Epoch40` in `STACKS_EPOCHS_MAINNET`. **zc-claim-helper-v2's own header contradicts this**: lines 6-8 say "block limits read_count 15,000 / read_length 100M / runtime 5e9 / write_count 15,000 / write_length 15M" (the 2.1 table), so its "45 percent of the block's read count" at 200 all-BTC entries is 22.5 percent under the real budget. The app's cost model built on the helper's header is twice too pessimistic on reads.

6. **Mainnet runs stacks-node 4.0.2**, not 4.0.1 (`/v2/info` `server_version: "stacks-node 4.0.2 (1b57c3f, release build, linux [x86_64])"`). Constants are identical at both tags; the prompt should say 4.0.2.

7. **The simnet toolchain reports the 2.1 limit table at epoch 4.0.** `@stacks/clarinet-sdk` 3.24.0 with `epoch = 4.0` returns `limit: {readLength: 100000000, readCount: 15000, ...}` in its cost output. Percentages computed by the SDK (or by Clarinet's cost reports) are half the real epoch 4.0 read budget. The table in section 6 uses the verified constants.

8. **pox-5 distributions.** Confirmed from source: `(define-read-only (burn-height-to-distribution-index (height uint)) (/ (- height (var-get first-burnchain-block-height)) (/ (var-get pox-reward-cycle-length) u2)))`, `pox-reward-cycle-length` is `u2100` on mainnet, so one distribution per 1,050 burn blocks, two per cycle. `calculate-rewards` (permissionless) must run once per distribution before a signer's `claim-rewards` returns anything (`ERR_DISTRIBUTION_ALREADY_COMPUTED` guards double computation; `claim-rewards` asserts `(> total-rewards u0)`). None of the three managers call `calculate-rewards`; the app's pull step should.

9. **`get-staker-unclaimed-rewards-for-cycle` is only the settled part.** Confirmed: it is `(default-to u0 (map-get? staker-unclaimed-rewards-for-cycle ...))`, while `get-earned-staker-rewards` is `(+ pending (/ (* shares (- rpt-current rpt-paid)) PRECISION))`. Use the latter.

10. **`claim-staker-rewards-for-signer` writes before the manager can check anything and never errors for a zero staker.** Source: it calls the private `settle-staker-rewards`, then `(map-set staker-unclaimed-rewards-for-cycle {...} u0)` and returns `(ok rewards-info)`; the only `err` is the reentrancy guard. It does not check that the signer pulled the cycle. Consequence for batching: a post-call precondition failure cannot be rolled back inside one transaction. Design decision 9 in the contract header handles it (one pox-5 load per entry, cycle deficits, pool-wide gate). The prompt's precondition list ("cycle pulled ... treasury or sBTC balance sufficient") is satisfied, but "cycle pulled" is now `ERR_CYCLE_NOT_PULLED (u1030)` up front, and a shortfall against the pulled reserve no longer rejects the settle (Max 500 returned `ERR_NO_CLAIMABLE_REWARDS`); it is booked as a deficit funded by the next pull.

11. **`convert` is not permissionless.** The prompt asked for a permissionless `convert` with a caller-supplied floor. An independent review of the contract found what that allows: anyone moves either pool, calls `convert <epoch> 0`, buys back; both on-chain quotes are read in the manipulated state so the route comparison does not protect; and `convert u1` freezes the open epoch at will. `convert` is therefore gated to admins and principals enabled with `set-converter` (an operator bot key without admin powers). This matches the project brief ("the pool operator should be able to make the payout/conversion") and contradicts the prompt's design point 3.

12. **Fill or fail (2026-09-20 revision).** `convert (amount-sats uint) (min-ustx-per-sat-x8 uint)` now swaps the tranche in full or fails: a route whose quote cannot absorb the whole tranche is not a candidate (`quote-routes` reports `dlmm-filled`), and a swap that moves fewer sats than the tranche fails the transaction with `ERR_PARTIAL_FILL (u1031)`. The floor is a rate (micro-STX per sat times 1e8) so the same floor works for any tranche size. When the last candidate route fails, its own error code is returned; `ERR_NO_ROUTE (u1020)` means no route quoted. A tranche smaller than the epoch remains the operator's tool for epochs larger than either pool; stakers are paid once, at the epoch's blended rate, after the epoch closes.

13. **Re-settling is legitimate.** With two distributions per cycle, a second settle of the same (staker, cycle, bond-index) after the second distribution is correct. "Already settled" is refused with a distinct code only when nothing accrued since: `ERR_NOTHING_TO_SETTLE (u1018)`; a never-settled zero keeps `ERR_NO_CLAIMABLE_REWARDS (u1001)`.

14. **Payout unit changes for STX electors.** `payout` and `claim-staker-rewards` keep their Max 500 return types, but `amount`/`earned` is micro-STX for an STX elector. Zero to Claiming must read `get-payout-currency` before labelling amounts. `claim-staker-rewards` for an STX elector whose epoch is not yet converted returns `(ok {earned: <settled sats>, withdrawal-request: none})` and prints `claim-awaiting-conversion`; it moves no funds.

15. **`fastpool-1-signer-manager` is the reference lineage with the tuple return.** `SP21YTSM60CAY6D011EZVEVNKXVW8FVZE198XEFFP.fastpool-1-signer-manager` (22,278 bytes, sha256 `f2473cfb53c3e5284149ec9f1d38f0ad66d70c8b1d04df1a7daa07e715b9bc3d`): `MAX_BIPS u10000`, `update-fees` asserts `(< new-fees MAX_BIPS)`, no last-admin guard, `claim-staker-rewards` returns `(ok {earned, withdrawal-request})`. The "uint-returning revision deployed as Xverse's manager" is a fourth deployment not among the sources read.

16. **Ledger 0.26.x blind-signs `(some ...)` too.** Zondax ledger-stacks issue #239 lists list, tuple, buff, string-utf8, `(some ...)`, `(ok ...)`, `(err ...)` and string-ascii over 60 chars as triggers; only int, uint, bool, none and principals are clean. So the single-entry `settle-staker-rewards (principal uint (optional uint))` is Ledger-clean only for `bond-index = none`; a bond staker's `(some u3)` requires blind signing on 0.26.x. The fix (128-item display budget, buffers over 64 bytes, non-ASCII) is "not released yet" at time of reading. Post-conditions and arguments share the 128-item budget.

17. **SIP-040 could not be read from docs.stacks.co.** `https://docs.stacks.co/concepts/transactions/post-conditions` returns 404. stacksgov/sips PR #279 ("Update SIP-030 text (wallet interface) with new postcondition modes") exists. Relevance for this contract: `convert` moves sBTC out of the manager contract and STX into it; originator-mode post-conditions on the caller do not describe contract-held asset movements, so the operator's wallet flow for `convert` needs the post-condition mode that admits contract transfers, or explicit contract-principal conditions.

18. **Hiro API is blocked by the organisation egress allowlist** from both the cloud workspace and the shell on the Mac (`X-Proxy-Error: blocked-by-allowlist`), and JavaScript `fetch`/XHR are blocked inside the built-in browser. All sources were read by navigating the built-in browser to `api.hiro.so` GET endpoints; POST read-only calls (`/v2/contracts/call-read`, `/v2/map_entry`) were not possible (a form POST reaches the API but is refused: "Invalid content-type: expected application/json"). Bin balances were recovered from the pool's `update-bin-balances` print events instead of the map. The reference contract bytes were verified by sha256 after writing.

19. **Hiro `/extended/v1/address/{contract}/balances` times out** for the DLMM pool (HTTP 500 "canceling statement due to statement timeout"); `/extended/v2/addresses/{contract}/balances/stx` and `/balances/ft` work.

20. **Clarity 6 `as-contract?` constraints found while building.** A `try!` inside an `as-contract?` body is a function-level early return, so it only type-checks inside a function whose return type is a response; an `as-contract?` body that ends in an unchecked response is rejected ("intermediary responses in consecutive statements must be checked"). The contract wraps each swap in a response-returning private function (`dlmm-swap-once`, `swap-velar`). Also: `match` is not allowed on a response whose err type is indeterminate; the deployed read-onlys `get-pool-for-swap`, `get-bin-balances`, DLMM core `get-pool-by-id` (`(ok (map-get? pools id))`) and Velar `get-pool` all return bare `ok`, so they are read with `unwrap-panic`, which cannot fire. The mock for `get-pool-by-id` initially had the wrong shape (bare optional); the review caught that a mainnet publish would have failed analysis. Every other mock return type was then checked against the deployed source.

21. **Testnet has no DEX pools.** Testnet pox-5 `ST000000000000000000002AMW42H.pox-5` and sBTC `SN3VMHXEN64ZZF71JQ5VESXDWTR301XTTXGF4J8F1.sbtc-token` / `sbtc-withdrawal` / `sbtc-registry` exist with the functions the manager calls (interfaces read). The DEX principals do not, and a deploy fails analysis on missing callees, so the testnet set (`build/gen-testnet.mjs`) points the manager at the real testnet pox-5 and sBTC and at the mock DEX contracts deployed under the deployer. Testnet cannot test the real swap, as the prompt anticipated.

22. **The vitest runner cannot start in the build sandbox** (forks pool), so tests are plain node scripts on `@stacks/clarinet-sdk`; the Clarinet binary was not installable (GitHub release assets blocked). `Clarinet.toml` is standard and `clarinet test` should work elsewhere after adding a vitest config.

## 3. Verified facts carried into the design

- pox-5 `signer-manager-trait`: `(validate-stake! (principal uint uint uint uint bool (optional (buff 500))) (response bool uint))`; `stake` passes `first-reward-cycle num-cycles amount-ustx u0 false calldata`; `stake-update` passes the new total lock as `amount-ustx`. Implemented exactly.
- pox-5 `register-signer` asserts `(is-eq contract-caller signer)`; `grant-signer-key` asserts `(is-eq contract-caller signer-manager)`: `register-self` unchanged from Max 500.
- pox-5 `claim-rewards` uses `contract-caller` as the signer and transfers via `as-contract? ((with-ft ... sbtc-token "sbtc-token" total-rewards))`.
- Max 500 fee API kept byte for byte: `fees-bips` var, `get-active-fee-bips`, `get-pending-fees` (`{active-bips, pending-bips, activation-cycle}`), cap `(<= new-fees u500)`, increases delayed `FEE_ACTIVATION_DELAY_CYCLES u2`, decreases immediate. Tested.
- `authorize-admin` requires `contract-caller == tx-sender`; batch functions are permissionless; `convert` uses the same caller test plus the converter role.
- Live state 2026-09-19 (burn 967730, stacks tip 9027030): pox-5 `first-pox-5-reward-cycle` 141, current cycle 143, `total-sbtc-staked` 16,016,067,436 sats (160.16 sBTC), `reserve-balance` 152,669,889 sats, `last-accounted-rewards-only` 62,201,557 sats. Max 500: `earned-fees` 3,744,989 sats, `total-pending-payouts` 75,330 sats, `total-unclaimed-rewards` 475 sats, sBTC balance 3,906,152 sats; deployed 2026-07-31 at burn 960,395. At 450 bps that fee total implies roughly 83 million sats gross through Max 500 over about 3.5 cycles, i.e. on the order of 12 million sats (0.12 sBTC) per distribution for a Max-500-sized pool. ## 7. Sizing

Verified inputs: tenure budget 30,000 reads (section 2.5); miner default `tenure_cost_limit_per_block_percentage = 25` ("a block can use at most 25% of the tenure's currently available cost limit", `stackslib/src/config/mod.rs`, both 4.0.1 and 4.0.2); `DEFAULT_CONTRACT_COST_LIMIT_PERCENTAGE = 95`; a transaction that alone exceeds the remaining block budget is skipped for that block (`BlockCostLimitError`) and retried in the next, and one that exceeds the whole budget is marked invalid (`TransactionTooBigError`).

Consequences:
- The real per-block ceiling for one transaction is 25 percent of the *remaining* tenure budget, not 5 percent. Early in a tenure that is 7,500 reads; after a few busy blocks it shrinks (25 percent of what is left). A transaction near 20 percent of the tenure (6,000 reads) fits only in a fresh tenure's first block or after a tenure extend; at 10 percent (3,000 reads) it fits while at least 40 percent of the tenure budget remains; at 5 percent (1,500 reads) while at least 20 percent remains.
- Native batch sizes for those targets, using 21 reads per settle entry: 5 percent = 71 entries, 10 percent = 142 entries, 20 percent = 285 entries (above the 200 cap; 200 entries = 14 percent). For payout-many at 15 reads per entry: 100, 200, 200.
- Recommendation: keep the 200 cap, default the app to 100-entry settle batches (7 percent) and 200-entry payout batches (10 percent), and treat 200-entry settle batches (14 percent) as an operator option that may wait a block or two. Measure on testnet with `scripts/testnet-batch-bench.mjs` at 71, 142 and 200 entries and record blocks-to-inclusion; testnet miners run the same defaults but far emptier tenures, so mainnet latency will be worse, not better.

Audit note (2026-09-24): the mock pox-5 does far fewer map reads per `claim-staker-rewards-for-signer` than the deployed pox-5, so the read count above is a floor for mainnet; read bytes are close. The fork simulation's lifecycle profile reports the real per-entry read count; size the first mainnet batches from it, and expect the practical ceiling to be nearer 100 entries than the 200 the list type allows.

## 10. Jing route C (contract B; rebuilt 2026-09-23 on the v3 generation market)

Target market: `SPV9K21TBFAK4KNRJXF5DFP8N7W46G4V9RCJDC22.markets-sbtc-stx-jing-v6` (deployed block 8994224, source 99,254 bytes read 2026-09-23; paused by its owner since 2026-09-21 pending `-v6-3`). token-x is sBTC, token-y is STX. It is a resting book with takers: makers deposit at a limit (STX per BTC times 1e8), any taker `swap` or any `settle-with-refresh` clears the book pro rata at the Pyth Lazer price carried in the caller's signed update, pushes STX to makers, rolls each maker's remainder into the next cycle or refunds it when below `min-token-x-deposit`, and advances the cycle. A maker crowded out of the 50 seats is parked, not refunded. Fees 10 bps per side, taker rebate 20 bps returned when unused. The market's `swap` is itself fill or fail (`ERR_PARTIAL_FILL u1017`).

Built in B (about 420 lines, `;; @jing` marked):

- Maker path, admin or converter: `jing-deposit (amount-sats limit update)` freezes the convert epoch and rests the sats; `jing-reconcile` books whatever filled since (idempotent); `jing-set-limit (limit update)`; `jing-cancel` (Jing refunds the resting amount, or the parked amount when nothing rests; with both, call twice). One order at a time.
- Taker path: `jing-swap (amount-sats limit min-ustx-per-sat-x8 update)` sells a tranche against resting STX bids at once, fill or fail at Jing, caller floor as in `convert`. Realized amounts are the contract's own balance deltas inside the call.
- Fill sensing is bounded by the order and needs no reconcile window: remainder = deposit under Jing's current cycle plus parked (`jing-holding`), STX received = balance above `ustx-liability`, sBTC refunded = balance above the reserve, both capped by what left the order. A stray transfer before a reconcile can only move value toward the epoch's stakers (tested).
- Every market call forwards the caller's signed Lazer update `(buff 8192)`; the market ignores it when no fresh price is needed. B reads no oracle.
- Errors: `ERR_JING_ORDER_OPEN u1032`, `ERR_NO_JING_ORDER u1033`; Jing's codes offset by u2000 (u3001 below minimum, u3007 paused, u3009 nothing to settle, u3016 limit would cross the book, u3017 partial taker fill, u3018 resting position). Gates while an order is open: `convert`, `jing-swap`, `sweep-stx`, `abandon-epoch`.
- Reads: `jing-current-cycle`, `jing-holding`, `get-jing-order`, `get-sats-in-jing`, `get-jing-state` (cycle, totals, min deposits, holding, order).
- Mock `contracts/mocks/markets-sbtc-stx-jing-v6.clar` (maker side, parking, pro-rata settlement with rollover and small refund, taker swap with rebate and fill-or-fail, pause; test controls `mock-set-price`, `mock-buy`, `mock-drain-bids`, `mock-park`, `mock-settle`, `mock-set-paused`, `mock-set-min-x`). 110 checks in `tests/jing.mjs`.
- Costs (simnet): `jing-deposit` 43 reads / 10 writes; `jing-reconcile` 53 / 7; `jing-cancel` 60 / 9; `jing-swap` 99 reads / 28 writes.

## 11. spox reward-claim-registry compatibility (2026-09-23, corrected 2026-09-24, decided 2026-09-24)

Daniel (core dev) named the trait that matters beyond `pox-5.signer-manager-trait`: `reward-claim-signer-manager-trait` in `stx-labs/spox` `contracts/contracts/reward-claim-registry.clar` at commit `ab8966fdc49f671c16a2d0b22bf65fdf299bb3a1`, lines 1 to 50. The registry lets a sponsor prepay claim installments for a staker; spox then calls the signer-manager's `claim-rewards` (when pox-5 still shows rewards owed to the signer) and `claim-staker-rewards`, and later `settle-accepted-withdrawal` / `reclaim-failed-withdrawal` for L1 payouts. The registry is not deployed yet (that revision points at the testnet pox-5).

**The type conflict.** The spox trait declares `settle-accepted-withdrawal` and `reclaim-failed-withdrawal` as `(response bool uint)`. That follows the pinned reference `SP3TB3AJ0XMZ9S6CGY2CQ6R06H1Z6DJQ1SH15ZP2H.signer-manager-stillearly`, which returns `(ok true)` from settle and the raw `as-contract?` response from reclaim. `SPMPMA1V6P430M8C91QS1G9XJ95S59JS1TZFZ4Q4.fastpool-max500-signer-manager` changed both to return the refunded sats, `(response uint uint)`, when it added fee-refund crediting (`staker-refunds`, `credited-refunds`, `claim-refund`); the Max 500 source states no reason, the inferred one is that a computed refund is worth returning and `reclaim` was made symmetric (its `as-contract?` is wrapped in `try!` so allowance codes no longer leak as function errors). One function cannot carry both types, and `impl-trait` compares signatures exactly: a Max 500 derived manager with `(ok refund)` fails deploy analysis against the spox trait ("invalid signature for method 'reclaim-failed-withdrawal'").

**Decision (Werner, 2026-09-24): adopt the spox trait unchanged; give up Max 500's `(ok refund)` values.** A and B return `(ok true)` from both functions and `impl-trait` the published trait `SP3TB3AJ0XMZ9S6CGY2CQ6R06H1Z6DJQ1SH15ZP2H.reward-claim-signer-manager-trait` (block 9050280, tx `0x11d2d90f4240f5c9677ce3186117f831a13b5c8ed0edfd43622e9bd3d957f520`, spox text verbatim apart from the header). Design decision 15 in both contract headers records this. What changed: the value inside `ok` on these two functions, nothing else. Logic, error codes, events, `claim-refund`, `get-staker-refund` and every other public signature are Max 500. The refund amount is still emitted (`amount-sats` on reclaim, `fee-refund` on settle) and the credited total is readable through `get-staker-refund`. What is lost: an on-chain caller doing arithmetic on the return of these two calls; none exists in the reference set (registry tests `is-ok`, `zc-claim-helper-v2` and PlanBetter do not call them). Lineage detection by Zero to Signing, Zero to Claiming and Leather keys on names and arguments, which are unchanged. The earlier corrected trait (`reward-claim-signer-manager-trait`, `(response uint uint)`) is withdrawn and moved to `_to_delete/`; it was never deployed.

**Why the registry works with Max 500 anyway.** A dynamic `contract-call?` through a trait argument is not rejected at runtime for a return-type difference. Verified 2026-09-24 in simnet: the trait-check mock with the published `bool` text accepted A while A still returned `(ok refund)`, 9/9, including both withdrawal calls reaching the manager. So spox will operate against existing Max 500 managers; only `impl-trait` at deploy needed the change. The 2026-09-23 note that "Max 500 conforms" was true structurally and false for `impl-trait`; this section supersedes it.

**Fork simulation consequence.** The first fork run (2026-09-24, block 9053249) failed to deploy A because A then pointed at the undeployed `-v2` trait. With the published trait the deploy step needs no precondition; the runner still checks Hiro and would deploy the trait in the fork if it were absent (fork taken before block 9050280, or a re-pointed trait).

Verified in simnet (`tests/traits.mjs`, 9 checks, mock trait text equal to the published trait): A and B pass as trait arguments; a registry style pull works; `claim-staker-rewards` pays an sBTC staker; for an STX elector it settles into the epoch and returns `{earned: sats, withdrawal-request: none}` (event `claim-awaiting-conversion`), and the next installment pays the converted STX through `payout-core`; both withdrawal functions reach the manager through the trait. `tests/invariants.test.mjs` checks the `(ok true)` return and the refund events on a rejected and on an accepted withdrawal (187 checks per build). Two things to know for the spox integration: the registry burns an installment on every `claim-staker-rewards` that returns ok, so an STX elector whose epoch is still converting spends one installment on the settle and gets the STX on a later installment or on the operator's `payout-many`; and the registry passes `(list)` as bond periods for STX stakes and `(list idx)` for bonds, both accepted by `claim-rewards`.

## 12. Open design questions after the FastPool PR 1 comparison (2026-09-23)

Decided: immutable single contract with pinned routes (kept); Max 500 surface with bonds and BTC calldata (kept, inherited at zero cost).

Open, with the current recommendation:

1. **Scale accounting (share mirror).** FastPool mirrors shares locally and never calls pox-5 per staker, about 10x more stackers per block than the pox-5 path here (each pox-5 call is charged its ~136 KB source). An API cannot change this: the cost is in the transaction that pays, not in discovering who to pay. If the goal is one audited manager that every pool can adopt, the mirror is the scaling path; it costs a second source of truth (drift on `unstake`, `repair-mirror-many`, pox-5 per staker ledger never zeroed) and a bigger audit. Recommendation for this deployment: keep the pox-5 path (200 entries per `settle-many`, about 14 percent of the tenure read budget; thousands of stackers is tens of transactions per distribution). Revisit if adoption by large pools becomes the goal; FastPool's mirror is under a public audit bounty and could be reused.
2. **Jing v2 versus the v3 generation.** Route C pins `sbtc-stx-0-jing-v2` (Pyth on-chain storage via VAAs, blind auction, live but thin). FastPool pins `markets-sbtc-stx-jing-v6-3` and `swap-router-sbtc-stx-jing-v5-3` (Pyth Lazer, resting book with takers, router across Jing, DLMM, XYK and Velar), which are not deployed yet; the deployed `-v6` and `-v5` are. The Jing section here is isolated (route id 3, `jing-*` functions, about 500 lines) and can be replaced by a v6 route without touching the DEX routes or the epoch model. A v6 route takes a signed Lazer update `(buff 8192)` as a call argument and forwards it; the manager reads no oracle itself. Recommendation: do not pin `-v6-3` before it exists; decide between shipping with v2 now and redeploying for v6 later (accepted on 2026-09-20) or waiting for `-v6-3`.

   Chain check 2026-09-23 (Hiro API): `SPV9K21TBFAK4KNRJXF5DFP8N7W46G4V9RCJDC22.sbtc-stx-0-jing-v2` has 72 transactions in total and none since 2026-05-08, when the owner called `set-paused` twice and the last depositors cancelled. The market route C pins has been idle for four months. `SPV9K21TBFAK4KNRJXF5DFP8N7W46G4V9RCJDC22.markets-sbtc-stx-jing-v6` has 16 transactions in total; the owner called `set-paused` on 2026-09-21 after depositors cancelled, and deposits since then abort. `markets-sbtc-stx-jing-v6-3` and `swap-router-sbtc-stx-jing-v5-3` return 404. An audit repository for markets v6-3 was updated 2026-09-22. Reading: v2 is dead, v6 is paused for the v6-3 migration, v6-3 is imminent. Route C as built cannot serve as a backstop.

   Decision 2026-09-23: two contracts. `signer-manager-stx-payout` (A) has no Jing route and can be deployed now: DLMM and Velar with fill or fail, `abandon-epoch` as the exit. `signer-manager-stx-payout-jing` (B) carries route C; it still pins `sbtc-stx-0-jing-v2` today and is rewritten for `markets-sbtc-stx-jing-v6-3` when that contract exists (see section 14). B is the source of truth; A is generated from it (`build/gen-nojing.mjs`, `;; @jing-begin` / `;; @jing-end` blocks, `;; @jing` lines, `;; @nojing` replacements), so everything outside the Jing route is byte identical between the two.
3. **Fair price without an oracle.** The DEX routes protect stakers with the converter's floor plus fill or fail; the failure mode of a careless floor is a bad fill, of a tight floor a failed transaction. Optional defence in depth without a per-transaction oracle input: read the stored Pyth price from `pyth-storage-v4` and refuse a realized rate more than X percent below it when that price is fresher than N seconds (about 30 lines). The runbook rule is stronger than the code: floor from a fresh `quote-routes` minus a fixed tolerance, every time.
4. **Exit for an unconvertible epoch: built as `abandon-epoch` (2026-09-23), stranded path added 2026-09-24.** Admin any time; anyone once the convert epoch is stranded, `STRANDED_EPOCH_BURN_BLOCKS u4200` burn blocks (two reward cycles) after its last progress (first settlement into it, each `convert` tranche, each Jing order placed or re-priced), `ERR_EPOCH_NOT_STRANDED u1034` before that. The clock is `progress-burn-height` in the epoch record against `burn-block-height`: no pox-5 read, one comparison. In B `jing-cancel` and `jing-reconcile` open to anyone at the same moment. `get-pending-conversion` reports `progress-burn-height`, `stranded-at-burn-height` and `stranded`; `is-convert-epoch-stranded` is the read-only. This resolves audit M-1 (Werner's decision, after the earlier no-timer decision of 2026-09-23). FastPool PR 1 uses the same shape with 432 burn blocks; two cycles here because conversion is an operator decision without a fixed schedule. It closes the convert epoch: the converted part pays in STX at the blended rate, the remaining sats pay back as sBTC pro rata through the Max 500 `pending-payouts` leg, so a staker with both legs is paid in two `payout` calls (sBTC first; `payout-many` twice). Refused while a Jing order is open (u1032) and when nothing is pending (u1022). `payout-core` now crystallizes before reading the sBTC leg. Lost admin and converter keys now delay STX electors by at most two cycles instead of stranding them; several admins and a converter key remain the way to a faster exit. Header design decision 14. 73 checks (A) and 80 (B) in `tests/abandon.mjs`. Applies unchanged to a future Jing v6 route: a partly filled resting order is cancelled and the residual goes through `convert` or `abandon-epoch`, the 100 percent rule stays.

5. **Scale is not a hard limit.** Nothing caps the pool size. `settle-many` and `payout-many` take up to 200 entries per call; a pool with N stakers needs N/200 transactions per distribution, each about 14 percent of the tenure read budget at the 4.0 limits, which fits the default 25 percent per block miner setting. 10,000 stakers is 50 transactions twice per cycle, or stakers and spox claiming for themselves. The mirror in FastPool changes the per-transaction cost, not whether a pool can grow. Nothing needs changing after deployment for a big pool; it needs a keeper that sends more transactions.

## 12a. Comments and read cost (measured 2026-09-23)

Comments are part of the stored source, and the source length is what every `contract-call?` into the manager is charged as read length (and, linearly, runtime) when the contract is loaded. Measured in simnet with contract A deployed twice: with comments 72,426 bytes, a call loads 72,445 bytes of read length; stripped of every `;;` comment 46,883 bytes, a call loads 46,902. Deploy costs are identical. So comments cost about 25 KB of read length per transaction that calls the manager (native batching loads once per transaction; an external batcher pays it per entry), which is 0.013 percent of the 200 MB tenure budget per call, or 2.5 percent for a 200-entry external batch. The structure hash ignores comments, so a stripped deploy would still verify against the same hash; the price is that the design decisions in the header are no longer on chain next to the code. Decision: deploy with comments.
